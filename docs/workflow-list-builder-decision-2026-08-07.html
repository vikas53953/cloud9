DESIGN / DECISION · 07 AUG 2026

Workflow list / builder for Cloud9

A deliberately small product decision grounded in a fresh, read-only Buzz observation and Cloud9's existing relay, task, approval, and run seams.

No production implementation shipped

A

Recommendation

Ship a manual reusable runbook in v1: a named workflow contains ordered agent steps, and a person presses Run. Each step uses the normal Cloud9 task path, keeps the current approval gates, and leaves an inspectable run history. Do not add schedules, event triggers, filters, or a graph canvas yet.

This is the smallest value that fits “agents are employees,” avoids inventing clocks, never starts silent work, and can reuse the current relay store and approval model.

What Buzz visibly proves

Installed Buzz, observed read-only on 2026-08-07. The screen has a Workflows rail item, Refresh, Create Workflow, and a clear first-workflow empty state.

Observed builder surface

Opening Create Workflow (then closing it without saving) showed:

  • channel assignment and an Edit as YAML control
  • name, optional description, enabled checkbox
  • Message Posted trigger and optional evalexpr filter
  • ordered Add step; initially “No steps yet”
  • Cancel, disabled Create, and Close

Buzz is evidence for a legible list + empty state + explicit builder. Its trigger/filter behavior is reference material, not a v1 Cloud9 commitment.

Other screenshots were checked for context: Agents shows managed workers and running state; Projects has a similarly calm empty state; Inbox/Coding show Cloud9-like channel work. No Buzz workflow was created or sent.

Three compact concepts

A

Manual reusable runbook

Named, ordered agent steps; a user presses Run. Existing approvals and task/run history remain authoritative.

  • Smallest accessible editor
  • No hidden timing or event grammar
  • Useful on day one
B

Triggered automation

Schedules or events start a workflow, with filters and enabled state like the observed Buzz form.

  • Could reuse Scheduler/HookBook seams
  • Introduces silent-work, ownership, and approval policy questions
  • Defer until trigger semantics are explicitly chosen
C

Free-form graph builder

Nodes and branches model parallel work visually.

  • High keyboard, 320px, focus, undo, and serialization cost
  • No matching Cloud9 persistence/execution model today
  • Defer; preserve ordered steps first

Proposed v1 contract

Surface
Add Workflows to the existing rail and route it through the same workspace/editor “one door” used by Tasks and settings. List and editor share the dark shell tokens. WCAG 2.2 AA is the target; this page is not a conformance claim.
Definition owner
The relay Store owns canonical SQLite-WAL workflow definitions. Store name, description, ownerId, channelId, version, ordered step snapshots, created/updated timestamps, and archivedAt. The engine never owns a second definition.
Step shape
Each step has a stable stepId, position, agentId, plain-language title, and prompt. Save a version snapshot so a later run remains explainable if the definition changes.
Run shape
Persist a workflow run with workflowId/version, requester, status, started/finished times, current step, error, and step snapshots linked to normal task/run records. Add optional workflowId/workflowRunId/workflowStepId links rather than a second execution protocol.
Trigger
Manual only. Run creates a queued run. No clocks, schedules, event filters, “enabled” automation, or auto-resume in v1. Existing AgentSchedule, Scheduler, and HookBook stay unchanged.
Execution
Serial ordered steps, one at a time. Each step creates a normal relay task. Stored agent policy decides whether its existing Approval is required; a workflow cannot disable or mint approvals.
Run history
List last status/time/current step; detail shows every step, task result, error, approval, and existing run record. Use bounded run retention already used by RUN_LIMITS. No raw secrets in definitions or history.
Permissions
Owner-only create/edit/archive/run in v1. Read visibility follows the channel. Every agent must pass existing mayDriveAgent; guests cannot spend someone else's runtime. Audit create/edit/archive/run and state transitions.
Existing Workflow tool
The provider’s Workflow helper ability remains an internal agent tool. The Cloud9 entity is a durable, explicit runbook; do not call or redefine that tool to execute it.
Non-goals
Schedules/cron, event triggers and filters, free-form graphs/branches/parallelism, YAML/code execution, silent retries, automatic resume, new approval semantics, publishing, or external side effects without the normal gate.

States and interaction contract

State language

  • List loading: skeleton rows plus a polite status region.
  • Empty: “No workflows yet” and “Create workflow”, mirroring the clear Buzz pattern.
  • Save success: list updates and announces “Workflow saved”.
  • Builder validation: first invalid field receives focus; errors are tied with aria-describedby.
  • Run: queued → running → waiting for approval → completed, failed, cancelled, or interrupted.
  • Failure says the exact step and reason; offer retry current/new run, never a silent retry.
  • On relay/app restart, active work becomes interrupted (“Cloud9 restarted before a result was recorded”); no automatic resume.
  • List/load errors have plain text and Retry. Unsaved navigation uses the existing leave guard.

Keyboard and responsive rules

  • Use semantic nav, headings, ordered list, buttons, labels, and a status/live region.
  • Focus the name field when the editor opens; restore focus to the workflow row after close/save.
  • Move up/down and remove buttons are available; drag is never the only reorder method.
  • Visible focus, no unexpected trap, and 24px minimum controls (prefer 44px).
  • Two-column list/detail on desktop; stack on narrow widths; reflow at 320 CSS px without a 2D graph or horizontal-only scroll.

One decision required before implementation

Should Cloud9 ship Concept A — manual reusable workflows only (named ordered agent steps, user presses Run, existing approvals and run history; no automatic triggers or schedules in v1)? Yes or no.

A “no” should name whether to pursue triggered automation (B) or a visual graph (C); this artifact does not silently choose either.
