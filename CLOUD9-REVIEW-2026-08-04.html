Cloud9 — outside review

4 August 2026 · read of C:\Users\vikasmit\cloud9 · three independent reviewers (hub, agent engine, desktop app)

The short version: this is a serious, well-built app, not a demo. The parts that are hard to get right — permission checks in SQL before the row limit, one-use download tickets, crash-safe database migrations, a chat renderer that cannot produce raw HTML — are done properly and the reasoning is written down next to the code.

Where it hurts: the same rules are enforced beautifully in one place and quietly skipped in another. Three of those gaps are serious enough that I would not put this on a shared or public network today. Every one of them is a small fix — the design is right, a handful of paths just walk around it.

The three that matter most

Critical 1

Any web page you open can take over the hub

The hub accepts WebSocket connections from anywhere with no origin check, and falls back to a password that is printed in your source code: dev-owner-token.

Browsers do not apply the same-origin rule to WebSockets. So while Start Cloud9.cmd is running, any website you visit in any browser can quietly connect to ws://127.0.0.1:8787, say hello with that token, and become the owner — read every channel, mint invites, and (because dev mode is on) start processes on your machine.

The packaged installer is safe: it generates a random 32-byte token and turns dev mode off. This is the workbench path only — but that is the path you use every day.

Fix: refuse to start when the token is the default and dev mode is off, and add a verifyClient that rejects any upgrade carrying a browser Origin header. A real client sends none.

apps/relay/src/server.ts:183, 221 · Start Cloud9.cmd:32
Critical 2

The owner key is encrypted at rest, then copied to a plaintext file

The main process stores the hub token with Windows encryption and 0o600 permissions — then the preload copies the decrypted value into the browser's Local Storage, which is a plain, unencrypted file under %APPDATA%\Cloud9.

That token is not a chat cookie. Owner rights let you create an agent, and an agent gets spawned with --add-dir <any folder>. Token equals read/write anywhere and run anything, as you. Any junk process running as your user — a bad npm install script, an infostealer — already scrapes those Local Storage files by default.

Your own code knows this rule: purgeLegacySecrets exists precisely because v1 kept the Claude key in localStorage, and the comment says that was wrong. The session token was then explicitly exempted from the purge.

Fix (the class, not the case): the renderer should never hold the value. Keep the token in the main process and expose a hello() call over the bridge; let main own reconnection.

apps/desktop/electron/preload.cjs:11-14 · apps/desktop/src/store.ts:708-714, 785-801
Critical 3

Two agent turns at once can read each other's channel history

Each agent turn writes its private access ticket to a file with a fixed name — .cloud9-mcp.json — and two turns per agent are allowed to run at the same time.

Agent "Scout" is in #general and #ops. Two messages land a second apart. Turn A writes its ticket; turn B overwrites it milliseconds later. Turn A's tool process starts after the overwrite, picks up B's ticket, and every history search turn A runs is answered with #ops content — which A then quotes into #general as fact. The channel re-check downstream does not catch it, because the ticket honestly says #ops. Also, whichever turn ends first deletes the file out from under the other.

Fix: put the turn's random id in the filename. The random value already exists in scope — it is a one-line change. The general rule worth writing down: any per-turn file gets the turn's id in its name.

packages/engine/src/claude-cli.ts:565-574, 477-482, 518-520

The pattern behind most of the findings

Theme

Every rule has a proper owner — and one or two paths that walk around it

This is worth fixing as a category rather than one bug at a time, because the same shape appears in all three parts of the app:

  • Secrets get stripped before spawning — by one shared function, with a name list and a shape regex. But CLOUD9_CRED matches neither (CRED ≠ CREDENTIAL), so on any machine started that way, your Anthropic key is handed to every child process — including Codex agents, which are a different account and which the code explicitly promises will never see it. One-line fix, biggest payoff on the list.
  • The SDK provider skips the stripper entirely and inherits your whole shell environment. If CLAUDE_CODE_OAUTH_TOKEN is exported on the box, the turn silently bills that account instead of the key you saved — and an inherited ANTHROPIC_BASE_URL would send your key to someone else's proxy.
  • Every hub request passes a permission gate — about forty of them do. activity passes none, so any invited friend can read the whole audit ledger: private channel names, approval sentences with private repo and branch names, every run summary. tasks and full agent definitions are broadcast to everyone too — including absolute paths on your disk like C:\Users\vikasmit\keys\mcp.json.

Class-level fix: make the switch statement default-deny with a default: that returns an error, and add one test that asserts every frame type has a gate. Same for spawning: no path builds an environment except through the stripper.

packages/shared/src/index.ts:3985 · packages/engine/src/provider.ts:388 · apps/relay/src/server.ts:493, 1911

Other high-severity items

High

A link in a chat message opens a real web page inside the app

There is no setWindowOpenHandler and no will-navigate guard, and there is no Content-Security-Policy anywhere. Every chat link renders as target="_blank", so Electron's default opens a child window that inherits the preload bridge. An agent that summarises a poisoned web page and emits a link gives that page access to setApiKey, setHubNetwork and the folder picker.

Fix: deny the window and hand the URL to the OS browser via shell.openExternal; block navigation away from the app's own origin; add a CSP with connect-src limited to the local hub. The CSP is also the second wall behind Critical 2 — right now there is only one wall.

apps/desktop/electron/main.cjs:435-458 · apps/desktop/index.html
High

The build downloads and runs a signing toolchain with no integrity check

prepare-packaging.mjs fetches an archive over the network, unpacks it, and electron-builder then executes it during npm run dist — with no checksum and no signature. electron-builder's own downloader verifies a hash; this script exists to bypass that path and dropped the check with it. Worse, the failure is swallowed with "carrying on", so a tampered or partial download does not even stop the build. A hijacked DNS or an intercepting proxy silently backdoors your installer.

Fix: pin the asset's SHA-512 and verify before executing. Three lines.

scripts/prepare-packaging.mjs:48-56
High

The installed app can be edited by anything running as you

asar: false plus a per-user install means the app ships as loose, editable files in a folder your account can write. The files list also ships the test files — including testkit.cjs, a fake safeStorage that does not encrypt — right next to the real main.cjs. Any user-level malware appends four lines and gets permanent execution inside the process that holds your decrypted tokens. There is no code signing on the Windows target either.

Fix: turn asar on, exclude *.test.cjs and testkit.cjs from the package, and sign the build.

apps/desktop/package.json:15-21, 33-36
High

One malformed message kills the whole agent host

The socket handler is JSON.parse(String(raw)) with no try/catch, and there is no uncaughtException handler anywhere in the repo. A truncated frame ends the process. Every running turn dies with it — and the cleanup blocks never run, so the MCP ticket file and a copy of your Codex OAuth token are left behind on disk. Every other send path in that same file is carefully wrapped; the socket entry point is not.

packages/engine/src/engine.ts:264
High

A second hello on one socket makes agents look alive forever

Each hello adds a brand-new connection object without removing the old one; close only removes the last. An engine with retry logic that says hello twice leaves a ghost behind, so the hub believes an engine is connected forever. Downstream: presence shows agents ready when nothing can run them, "Cloud9 isn't running on that computer" never appears, and project look-ups hang until timeout. One line: remove the old connection before adding the new one.

apps/relay/src/server.ts:254-286, 359-360
High

Once you pass 1000 approvals, expired ones become answerable again

The approvals query has no ORDER BY and applies its limit in JavaScript after reading the whole table. The expiry sweep only sees an arbitrary 1000 rows. An approval that ran out ten days ago but sits outside that window is still marked pending — and gets accepted. That breaks your own stated law that silence must never read as a yes.

Medium — correctness and speed

Medium

Things that will produce wrong answers, quietly

  • Search results can go to the wrong agent. Waiting searches are matched on the query text alone. Two agents searching "deploy" at the same time resolve each other's results; the channel filter then strips everything, and the tool confidently reports "Nothing in this conversation matches that — that is a real answer." A confident false negative in the one feature built to stop agents saying "I don't remember." Correlate on an id you mint, not on the user's words.
  • Job summaries can be borrowed from another job. The comment says the run is checked against the task before use; the code does not check. Two background jobs run by default, so this is reachable.
  • Files can be published into the wrong channel. Two turns for one agent share a working folder, and produced files are collected by timestamp, not by owner. A file made for #ops gets posted in #general.
  • Demo mode only fakes the model. Everything else stays real: !code creates real git worktrees and branches, !issue reaches the real gh CLI. Your QA script defaults to demo mode, so a QA sweep on a machine with a project connected can create real branches.
  • Your Codex OAuth token is copied into %TEMP% every turn, cleaned up only on a clean exit. No sweep at startup, and the chmod 0600 does nothing on Windows. After a few crashes there are live tokens lying around.
  • Task status and approval decisions are not checked at runtime. Send decision: "maybe" and the card becomes permanently unanswerable while the job is silently cancelled. The neighbouring handlers do validate — these two drifted.
Medium

What will make chat feel slow at real sizes

  • Channel lookup runs a query per channel, and it sits on the path of every send, history, react, mark-read and search. With 150 channels and 20 files in a room, one "add member" can fire tens of thousands of database calls on the single thread that serves everyone else.
  • Unread counts parse every unread message on connect. Someone returning after three months blocks the whole hub while it parses tens of thousands of rows. The exact count is the right product call — it just belongs in SQL, not a JavaScript loop.
  • The UI redraws everything on every frame. You built the selector layer that fixes this and then used it in 2 of 24 places; the other 22 subscribe to the entire world, so a presence tick re-renders every screen.
  • Notification toasts rescan all loaded messages on every change, sorting each channel every time, and the "already seen" set never shrinks.
  • No message virtualization — every loaded message is a live DOM node, so scroll-back grows the page without limit.

Polish and product gaps

Low

Against a Slack-like bar

Threads, search-everywhere, unread and mention counts, quiet hours, muting and OS notifications are all genuinely there and thoughtfully done. What is missing:

  • Drafts vanish when you switch channels. The composer's text lives in local state that unmounts on navigation. This is the most likely daily complaint on the list.
  • No typing indicator between people. Agent presence is richly modelled; person-to-person is not.
  • No permalink to a message and no jump-to-date.
  • The sign-in box is pre-filled with dev-owner-token — a value that is guaranteed to fail in a packaged build, shown on the one screen a real user reaches.
  • The hub will bind to any address you type, including hotel wifi, over unencrypted ws://. Both layers block only wildcards. Allow loopback and the Tailscale range; require a flag for anything else.
  • The mobile app is a prototype with a hardcoded LAN IP, a cleartext socket, an unguarded parse that silently freezes it, and it is not in the workspace list — so no test or typecheck ever touches it. Label it dead or remove it.
Low

Two structural things making the rest worse

App.tsx is 12,177 lines — 156 functions, 145 pieces of state, in one module. The comments are excellent and are clearly why it grew, but it is past what a reviewer can hold, and it is the direct reason two of the medium findings drifted. It is also large enough that plain text search tools treat it as a binary file and silently find nothing. Suggested split with no behaviour change: icons, notifications, settings, agents, chat.

There is no ESLint in the repo at all — no config, no lint script. The React hooks rule alone would have caught the settings screen bug where an effect reads a value it never re-runs on, leaving "Connected apps" permanently stale if you open Settings while reconnecting.

What is genuinely good

Strengths

These are above the bar for this kind of app

  • Download tickets. One-use, 30 seconds, memory only, permission re-checked at redeem against current state, ticket deleted before any check can fail, content type computed from an allowlist rather than trusting the uploader. The CORS decision is both correct and correctly explained — most codebases get that one wrong.
  • Permission filtering happens in SQL, before the row limit. This is the single most commonly botched thing in permissioned search, and the helper is defined once so the two query paths cannot drift.
  • Database migrations run their work and their version bump in one transaction, so a crash cannot leave shape and version disagreeing. The search index self-heals on an interrupted backfill instead of staying silently short.
  • The agent tool doorway is a real boundary. The search tool has no parameter that can name a channel, extra arguments are refused rather than ignored, and a fresh random ticket is minted per turn on loopback only.
  • The command runner refuses instead of escaping. Strict allowlist, throws rather than repairs, untrusted text goes on stdin, and it kills the whole process tree. The most carefully reasoned module in the repo.
  • The chat renderer cannot produce HTML — only React elements — so there is no escaping step a future edit can forget. The link checker rejects control characters before matching the scheme, so java\nscript: fails.
  • Credentials in the main process are handled correctly: OS encryption with an explicit refusal path instead of a silent plaintext fallback, and a migration that deletes the old plaintext copy only after the encrypted write is confirmed. Logs record lengths, never values.
  • Durability is proven, not asserted — the whole-file write has one owner, and the test kills a real process mid-write.

Where the tests are, and where they are not

Coverage

~470 tests, and they are good — but they are pointed away from the risk

Every finding above has a matching hole. That is not a coincidence; it is the diagnosis.

  • Both existing tests for the audit ledger send the request from the owner's socket — nothing asserts a guest is refused.
  • Nothing asserts what a guest receives on connect; no test anywhere mentions the fields that leak your disk paths.
  • No test ever runs two turns for the same agent at once — which is why three separate findings coexist there.
  • The secret-stripping tests only check the credential names that are already handled, which is exactly why CLOUD9_CRED slipped through. The SDK provider has no test at all.
  • The approval-expiry test uses a near-empty table — precisely the case that passes.
  • packages/shared has no test file of its own for its 4,495-line core, which holds the redaction rules, filename safety, and the "must ask before acting" logic. It is covered only indirectly, so deleting an unrelated relay test silently removes coverage of a safety rule.
  • Three .test.ts.new files sit beside the real tests and never run.

If I were fixing it, in this order

Plan

Cheapest-first, worst-first

  1. Add CLOUD9_CRED to the credential list. One line, stops your Anthropic key being handed to every child process including a different vendor's agent.
  2. Wrap the socket message handler and add a process-level crash handler. One block, stops a stray frame taking down every running turn and stranding secrets on disk.
  3. Put the turn id in the MCP config filename. One line, closes the cross-channel history leak.
  4. Refuse the default owner token, and check the origin on upgrade. Closes the browser-takeover path on the workbench.
  5. Move the hub token out of the renderer, and add the window-open handler plus a CSP. These three together are what turn "a bug" into "not exploitable".
  6. Pin the hash on the packaging download, turn on asar, drop the test files from the package.
  7. Gate activity, narrow tasks, strip disk paths from agent definitions — then add the default-deny case and the one test that says every request type has a gate.
  8. Then the speed work (channel lookup, unread counts, the selector layer) and the product gaps (drafts first).

Steps 1–3 are about ten minutes of typing and remove the two nastiest failure modes. Steps 4–6 are the difference between "safe on my laptop" and "safe on a network".
